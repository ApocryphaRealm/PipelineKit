## 1. A file changes only by passing through a versioned, gated process - never by appending

- **The owner set it:** 2026-08-27: "let's apply the same versioning logic from the mods, and let's treat the version MD files the same way we would treat the mods" (rules\06, rule 60; `docs-pipeline.ps1` header); 2026-08-27: "add version markers on the rule files so that the updates get rolled into a new file instead of referencing other rules" (rule 59 area; `rules-version.ps1` header; the original begins "maybe we should add"); 2026-08-27: "find a way to strictly enforce the versioning logic so that you don't keep getting it wrong" (rules\03).
- **The idea:** a change is a new revision that passed a check and left its predecessor archived, with a number nobody typed. Appending is cheaper than editing, so without the gate corrections arrive as new text referencing the old (rules), as numbers typed by hand (mods), as a second copy beside the first (documents). The gate makes the cheap path the wrong path.
- **Applied in:** mods - `version-gate.ps1` (rule 48: `bump` issues the number, `record` needs the binary's hash, `gate` refuses what it did not issue, `posted` spends the number - since 2026-10-11 only a posted build consumes one, the owner: "has to be posted to Nexus. To get a new number"; an unposted build, working or not, keeps its number and takes every further change; since 2026-10-21 `bump` also refuses to run without `-Kind patch|minor|major` - semantic versioning, the change kind is a required input, never a default; header: "There is no -Force"); rules - `rules-version.ps1` (rule 59: `check` fails an amendment by reference, `bump` archives the set and regenerates the digest, archives in `rules-archive\`); documents - `docs-pipeline.ps1` (rule 60: the governing set is stamped, references resolve, tracked constants agree; since step 10.1 it also stamps `.json` and `.txt` files, archive name `<basename>-v<X.Y.Z><ext>`); the rosters (`.MD\resolvers\rosters\*.json` carry `_version` and `_revised`, e.g. identity.json 1.0.0, 2026-10-09); packages - `package-mod.ps1` -> `package-gate.ps1` -> `pre-finalize-check.ps1` -> `finalize-mod.ps1` (one path, each step refusing); the changelog written as the change happens (rule 61); the install step's priority gate in `install-test-build.py` (step 3.1) checks the folder that will actually load.
- **The shape of a correct application:** one tool issues the number; the tool refuses what it did not issue; every superseded revision is archived, never overwritten; a number typed by hand is wrong until the tool agrees.
- **Not yet applied to:** memories (edited in place, no revision) [checked 2026-10-09: 470 memories plus the generated INDEX.md and MEMORY.md; a memory is still edited in place with no revision kept]; `gate-rules.json` itself (top-level keys are only `_about` and `rules`, no version stamp - verified today); the plan documents under `4. plans` (stamped by hand) [unverified]; the skills [corrected: skills are one copy now - `.MD\skills` junctioned into the home skills folder (step 7.7; optimizer section 11 "skills linked")] - but they carry no stamp [unverified]; the rosters [corrected: now stamped, see Applied in].
- **Built from these mistakes:** PAST-MISTAKES-LIBRARY.md "A rule enforced by several tools, each holding its own copy, is not enforced" (2026-09-12); "Mod version numbering: next = LAST WORKING + 1" (2026-08-28); "Two edit-tooling traps: the Write tool drops the spaces of whitespace-only lines, and Windows PowerShell 5.1 reads a BOM-less UTF-8 file as cp1252" [corrected: the BOM point sits inside that "Two edit-tooling traps" entry, not under its own heading].

## 2. Callers ask for a role; one resolver answers from rosters - nothing names a path

## 3. One home per kind; a second copy becomes an index line

## 4. A rule is enforced by one tool that refuses, not by several that remind

## 7. A verdict is a prediction, recorded with its evidence and scored when reality arrives

- **The owner set it:** 2026-08-27: "log how effective this process is in actually resolving an issue" (rule 56; `falsification-log.ps1` header); the research pass of 2026-08-29, PIPELINE-RESEARCH section 8 (error analysis on real traces; named in `gate-ledger.ps1`'s header).
- **The idea:** a gate that always returns the same verdict is a queue with extra steps, and it looks identical to a working gate until something it should have caught ships. Every judgement is recorded with its basis, counted as UNTESTED until something could have contradicted it, and a contradicted verdict is the most valuable entry because it says what evidence was available at verdict time.
- **Applied in:** the gate ledger for stage 1 classification and stage 8 compatibility (rule 58; `gate-ledger.ps1` header: nine verdicts, every one "Compatible", was the first finding); the falsification scorecard (rule 56: "3 correct out of 9 acted on, 33%" seeded baseline); the adversarial contest with "neither" as a first-class verdict (rule 57, `-Action contest`; the scorecard flags a judge that never returns it); the version ledger's `working` requiring the binary's hash (`version-gate.ps1` header).
- **The shape of a correct application:** record at the moment of the verdict, with evidence; resolve when reality arrives; warn when a gate has never returned its negative verdict; never merge the baseline with the method's results (rule 56: the report separates the pre-mode baseline from episodes under the method).

## 8. Attack the hypothesis before building the fix; compare against a working reference first

- **The owner set it:** 2026-08-27: "create a hypothesis for the issue, and you try to disprove your own hypothesis" (rule 56); "have them compete" (rule 57); "after 5 consecutive failures to fix something you have to pause and go into analysis mode" (rule 49); "part of the analysis is always to compare to working versions of other similar mods" (rule 49 area, rules\06 line 115).
- **The idea:** a hypothesis tested by fixing it is the most expensive and weakest test. ## 19. A wrong record is withdrawn by a recorded retraction checked against the source of truth, never by editing the record

- **The owner set it:** the version rules (rules 6 and 48): a number is spent by POSTING it, and numbers are never typed - one tool, role `version-gate`, holds every version rule. On 2026-10-25 two ledger rows (PinPluginsLast and HUDPositionManager) claimed a 1.0.0 had been posted that Nexus never published, and the tool had no supported way to take a claim back.
- **The idea:** a record that drives arithmetic (the next number is the last POSTED one stepped by the kind) cannot be fixed by hand-editing it - the ledger is regenerated from the event log, so the edit would vanish, and nothing would show it had happened. A wrong claim is withdrawn by an event of its own, made by the tool, that first re-reads the source of truth for that claim (the Nexus page) and refuses while the source still supports it. The withdrawn claim is kept beside the row with its evidence, not deleted, so the history stays readable.
- **Applied in:** role `version-gate`: `retract -Mod X -Version V -Evidence "..." [-WhatIf]` re-reads the Nexus files API, refuses while the page still publishes V, moves the claim from the row into a `retracted` field (status unchanged), and writes a `posted-retracted` event that `events.py`'s fold honours, so a regenerated ledger keeps the retraction; the ledger schema allows the field. First used 2026-10-25 for PinPluginsLast 1.0.0 and HUDPositionManager 1.0.0 (.MD 0db2d30); the last posted number stays 1.0.1 for both.
- **The shape of a correct application:** the withdrawal is a new event, never a rewrite of the old one; the tool checks the source of truth itself rather than trusting the caller's word; it refuses when the source disagrees; the withdrawn claim and its evidence stay on the record; a dry run (`-WhatIf`) shows the change first.
- **Not yet applied to:** `record` (a wrong "working" claim) and the compatibility ledger's verdicts have no retraction of their own; the Nexus API does not list deleted files, so a retraction proves only that the page does not publish V now, not that it never did.
- **Built from these mistakes:** the two wrong 1.0.0 posted rows (2026-10-25; no past-mistakes entry yet).
- **Checked by:** `scripts\tests\test_version_gate_retract.py` (13 checks), and the ledger-matches-event-log check (571 rows).
- **Topics:** versioning, ledger, gates, nexus.

## 20. Every task starts as an equation: inputs with their source of truth, relationships, output, check, assumptions

- **The owner set it:** 2026-11-16 18:12: "it seems like most of our issues or problem solving throughout this whole pipeline is or can be boiled down to something simple as a mathematical equation solving approach, like define the variables that take part in the equation, define the relationships between the variables and how they interact within the equation, and then produce the output for the equation. And it seems like we could standardize that somehow." Main Agent proposed the five-part card; the owner answered "Yes." at 18:17 (rules\06, rule 56 amended 2026-11-16).
- **The idea:** a fix, a build or a design is an equation solved for its output. It goes wrong in one of four ways, each a term of the equation: an input taken from the wrong place (a guess, a work folder, a manifest instead of the game skeleton, the shipped file, the live page); a relationship that holds but was never written down, so nobody applied it; an output nobody can check; or an assumption carried as a fact. Writing the five terms before the work turns each of those into something a tool can refuse - an input line with no source, an empty check, assumptions that say "none" without a reason - and makes the assumptions the first thing attacked, which is what the falsification episode is for: the hypothesis is usually one assumption taken as true, the killing condition is the observation that would show it false, and the other assumptions are the rivals.
- **Applied in:** role `problem-card` (`scripts\problem-card.py`; cards in role `problem-cards`, `.MD\problem-cards\<date>-<slug>.md`): `new --task T [--area A]` writes the skeleton, `check <card>` refuses (exit 3) a missing or empty section, an INPUT with no `source:`, a left placeholder, or ASSUMPTIONS that say "none" without a reason, `assumptions <card>` lists what to attack first. `falsification-log.ps1 -Action open` refuses without `-Card <path>` that passes the check (waived for `-Baseline`) and records the card on the episode. Rule 56 carries it (amended 2026-11-16); PREFLIGHT has the row; the troubleshooting skill's step 0.5 and `references\PROBLEM-CARD.md` hold the template and two worked examples; the mod-release and in-game-test skills point at it for builds and for test steps written from the card's CHECK.
- **The shape of a correct application:** every input names the place its true value is read from, and that place is the object itself (logic 9) or the file that is the truth for it (logic 16); relationships are written as constraints a check could test; the CHECK is mechanical where it can be - a gate is the best check; the ASSUMPTIONS list is honest and is attacked before anything is built; the card is written before the work, not reconstructed after it.
- **Not yet applied to:** `test-request submit` takes no card (recommended as an optional `--card` whose CHECK seeds the steps' EXPECTED results - not wired, because every session's request path goes through `combined-run.py` and a new required field would refuse requests already in flight); builds and design tasks that open no falsification episode have no gate that asks for a card - only the rule, PREFLIGHT and the skills [no refusal yet]; design taste is outside it by nature (the owner's eye is the final term, which is why option sheets exist), and so are unknown unknowns (testing and falsification flush them out).
- **Built from these mistakes:** four of 2026-11-16, each one term: bracers placed from the NPC Hand bone's head instead of where the visible hand starts (a misdefined input; PAST-MISTAKES-LIBRARY.md "Matching _0/_1 armour meshes came out with different vertex orders and triangles" carries the same exercise's cuff fit); ModEx grouping a form by its defining plugin, which hid the Skyforged swords (an unwritten relationship); nexus-files.json "replaces" left null (a missing input; "A new page's first update would have posted its files as new files, not new versions"); package-render output depending only on the NIF and DDS hashes, unused (a known relationship nobody applied; "Package renders started at posting time held a release for hours").
- **Checked by:** the `problem-card check` refusal and the `-Card` refusal on `falsification-log.ps1 -Action open`; `scripts\tests\test_problem_card.py` (27 checks) and `scripts\tests\test_falsification_log.py`.
- **Topics:** troubleshooting, hypotheses, gates, process, design.
