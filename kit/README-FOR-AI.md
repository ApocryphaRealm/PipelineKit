# README-FOR-AI - how to rebuild this pipeline (the recipe)

Pipeline Kit 1.1.0. You are an AI coding agent (Claude Code or similar) and a person has handed you this
folder because they want the pipeline it describes running on their machine, for their own mods. This file is the
recipe. Follow it in order; every step names the command and the check that proves it worked. Do not report the
pipeline as up until the self-test in step 6 prints `PASS`.

**Two things you must do, before anything else:**

1. **Read `OPTIONAL-SCRIPTS.md` and ask.** Nothing in this kit connects to the internet. That document lists the tools left
   out because they do: why each is needed, what it does, the service and what the person would supply. Ask the person,
   item by item, whether they are interested. Build one only after a clear yes to that item. Never build one unprompted,
   even when a rule or skill names it as if it were there.
2. **Respect other authors' permissions.** Before working on, patching or reading into a mod the person did not write, ask
   them to confirm they have checked its permissions, including Nexus's "Ask Me" setting for AI workflows: files under it may
   not be integrated into automated AI workflows without the author's written permission. If they have not, stop there.

## 0. What you are rebuilding, in one paragraph

A folder tree where the folder names ARE the pipeline (twelve numbered stages plus a `.MD` folder of governance), a
set of 70 standing rules split into seven parts and read at the moment they apply, a library of past mistakes that
is looked up by topic before acting, a short catalogue of the design ideas ("logics") the pipeline applies
everywhere, a set of gates - PowerShell and Python scripts - that refuse to issue a version number, package a build
or finalize a release unless the rules are mechanically satisfied, and a role resolver through which every script
finds every other script, data file and folder. The pipeline this came from ships Skyrim Special Edition mods to
Nexus Mods; the mechanism is not Skyrim-specific, and section 9 says which parts are.

## 0b. The layout, and calling things by role

After step 3 the tree looks like this (only the parts you will touch):

```
<ROOT>\
  1. mod sorter ... 13. testbench      the stage folders - the folder a thing sits in IS its stage
  pipeline.config.json                 what kit-install chose (root, MO2 instances); never a secret
  .MD\                                 governance: everything in this kit
    CLAUDE.md  RULES-DIGEST.md  PREFLIGHT.md  BANNED-WORDS.md    read at every session start
    rules\01-...07-*.md                the seven rule parts
    PAST-MISTAKES-LIBRARY.md           every failure and how it was caught (looked up by its index, never read through)
    LOGIC-LIBRARY.md                   the catalogue of logics: one design idea per entry, where it is applied
    skills\<name>\SKILL.md             procedures (Claude Code skills); their references\ hold the long procedure docs
    docs\  docs-archive\               reference documents
    scripts\                           ledgers, gate-rules.json, and the scripts that sit at the top level
      gates\                           every *-gate script: version-gate.ps1, package-gate.ps1, the helper gates
      release\                         changelog, pre-finalize-check, finalize-mod, the Nexus distro tools
      ops\                             session-digest, attention-ping, prockill
      plugins\                         ESP/FOMOD/NIF tools: esp-audit, make-fomod, make-espfe, fomod-destinations, Inspect-NifShapes
      render\                          the render work pipeline: niflib, winding, nif-readback, render_lib, before-after-sheet
      art\                             patternlib (the engraving pattern library), make-feature-banners
      git-hooks\pre-push
    resolvers\
      resolve.py  resolve.ps1          the role resolver (rule 70)
      rosters\*.json                   the roles: one name per script, data file, folder, policy number or public fact
      schema\                          JSON schemas the resolver checks the rosters and ledgers against
      session-start.py                 prints the SessionStart hook payload, generated from the rosters
      INDEX.md                         GENERATED by kit-install: every role and what it resolves to on this machine
```

**Call by role, never by path (rule 70).** A script never writes another script's path; it asks the resolver of its
own tree: `py -3 <ROOT>\.MD\resolvers\resolve.py find version-gate` prints the file; `run <role> [args]` runs it;
`place test-build-package --var game=Skyrim --var mod="My Mod" --var version=1.0.0` fills a pattern; `explain <role>`
shows how a role resolves; `check` proves every role names a file that exists (`--callers` also fails on a role a
script or document names that no roster defines). The resolver takes `<ROOT>` as the folder above the `.MD` it sits
in, so a copied tree answers inside itself - that is how the self-test's throwaway pipeline works. When a file moves,
change its role's `at` in one roster and every caller follows; leave a short stub at the old path only if something
outside the tree still calls it, and give the stub an expiry date. Do the same for yourself: a path remembered from
an earlier session is the commonest way a moved file gets called - `find` the role instead.

The rosters ship filtered: a role is in the kit only when the file it names is. The original's MO2 instances, its
one-off scripts and its machine's programs are not roles here; add your own (`kind` is file, dir, place, set or value;
`at` may use `{root}`, `{home}`, `{role:<other>}` and, for a place, `{variable}`), then run `resolve.py check` and
`resolve.py index --build`.

**Two libraries, two jobs.** `PAST-MISTAKES-LIBRARY.md` is the long one: a numbered entry per failure (symptom as the
heading, what was believed, what was true, how it was caught), with a generated index block of headings and topic
tags at the top (`scripts\logic-index.py` writes it - the name is historical). `LOGIC-LIBRARY.md` is short: each
entry is a *logic* - a design idea the pipeline applies across many places (versioning as a gate, calling by role,
one home per kind of thing) - with where it is applied. A failure goes in the first; a new mechanism gets an entry
in the second the same day.

## 2. Requirements

- Windows 10 or 11. The gates are Windows PowerShell 5.1 scripts (`powershell.exe`); PowerShell 7 also runs them.
- Python 3.10 or newer on `PATH` (`python --version`) **with the Python launcher** (`py -3 --version`; the python.org
  installer adds it): the scripts call the resolver as `py -3 ...\resolvers\resolve.py`, and the digest, the indexes,
  the plugin audit and the FOMOD maker are Python.
- For the render work pipeline (section 7e) and the model-mod rows of the package gate: the Python packages **numpy**,
  **scipy** and **Pillow** (`python -m pip install numpy scipy pillow`); the pattern library also uses **matplotlib**
  and **scikit-image**. The package gate runs the NIF rows on every package, so install numpy even for a pipeline
  that never makes a model mod.
- Optional, for renders: **Blender** (a recent version) with **PyNifly**, a third-party NIF add-on - the person
  installs it into Blender themselves; the kit never ships or copies any of it. And Microsoft's **texconv**
  (DirectXTex, not shipped), which the UV-overlap gate uses to decode DDS. Point the scripts at them with the
  `BLENDER` and `TEXCONV` environment variables, or put them on `PATH`.
- git 2.30 or newer. Rule 3 and rule 9 assume a public repo per mod; pushing to it is the person's step, because the kit
  pushes nothing.
- Optional, only for Skyrim mods: a C++ toolchain (CMake, vcpkg, MSVC) for SKSE plugins, Mod Organizer 2 for testing.
  The pipeline runs without them; the DLL-specific gate rules skip packages that ship no DLL.

## 3. Choose the root and install

Pick `<ROOT>`: a folder on a drive with room, whose path contains no characters PowerShell treats as wildcards
(`[`, `]`). The original was a folder named `Claude output`. Then:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\kit-install.ps1 -Root "D:\Pipeline"
```

What it does: creates the thirteen stage folders (`1. mod sorter` … `12. needs an update`, plus `13. testbench`),
creates `<ROOT>\.MD\` and copies every kit file into it in the layout of section 0b (so
`<ROOT>\.MD\scripts\gates\version-gate.ps1`, `<ROOT>\.MD\resolvers\resolve.py` and every role's file are real), writes
`<ROOT>\pipeline.config.json`, seeds the empty ledgers, fills in the Claude Code memory folder of `<ROOT>` in the
data roster (role `memory-folder`: `%USERPROFILE%\.claude\projects\<ROOT with every non-alphanumeric character
replaced by ->\memory`, the folder Claude Code uses when started in `<ROOT>`) and seeds it if it does not exist,
generates `resolvers\INDEX.md`, runs `resolve.py check`, and sets the `PIPELINE_ROOT` user environment variable. It
refuses to overwrite a `.MD` that already holds a ledger with entries.

**Check:** `Get-ChildItem <ROOT>` lists 13 numbered folders and `.MD`; `<ROOT>\.MD\scripts\version-ledger.json`
contains `[]`; the install printed `ok  resolve.py check: OK <n> roles in 7 rosters`.

### 3b. The person's public identity

`<ROOT>\.MD\resolvers\rosters\identity.json` holds the public facts the Nexus page rules check: the Nexus game domains,
which stay. Add a role for any other public link the person wants a gate row to check, then run
`py -3 <ROOT>\.MD\resolvers\resolve.py check`.

### 3c. The SessionStart hook (Claude Code, optional but recommended)

`resolvers\session-start.py --print` prints the payload a Claude Code SessionStart hook injects: the three files to
read, the rules version and count, where the past-mistakes library and the memory index are, and two live checks.
Add it to `%USERPROFILE%\.claude\settings.json` under `hooks.SessionStart` as the command
`py -3 "<ROOT>\.MD\resolvers\resolve.py" run session-start --print` - through the resolver, so the hook keeps working if
the file moves. Changing settings.json is a persistent configuration change: ask the person first.

## 4. Install the git hook (the first gate)

```powershell
git config --global core.hooksPath "<ROOT>\.MD\scripts\git-hooks"
```

The `pre-push` hook looks at what is about to be pushed, locally, and refuses added lines shaped like an API key. It is
global on purpose: every repo on the machine, present and future, with no per-repo step. Tell the person you are changing
a global git setting and ask first; `kit-install.ps1 -SetGitHooks` does it for you.

**Check:** `git config --global core.hooksPath` prints the path.

## 5. Tell the scripts about Mod Organizer 2 (only if the person tests in MO2)

Set `PIPELINE_MO2_INSTANCES` to a `;`-separated list of each instance's `mods` folder, for example
`E:\MO2\MyList\mods`. `pre-finalize-check.ps1` checks that a candidate build is installed there before it may
finalize, and `prune-test-builds.ps1` keeps one installed version per mod. In `scripts\gate-rules.json`, the rule
`installed-build-is-the-package` carries an `instances` list; put the same folders there. Without these the checks
report SKIP, never a false FAIL.

## 6. Run the self-test - the pipeline is not up until this passes

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "<ROOT>\.MD\scripts\kit-selftest.ps1"
```

It builds a throwaway pipeline in a temp folder from the installed kit (with `USERPROFILE` pointed at the temp
folder for its own run, so the memory folder the install seeds lands there and not in the person's `.claude`), checks
the layout and the resolver, and carries the example mod (`example\ExampleMod`, a one-file Mod Organizer 2 plugin,
chosen because it needs no compiler) through the stages a real mod takes:

0. the layout: no file in the installed tree is a retired-path stub; `resolve.py check` passes; `resolve.py find
   version-gate` answers `<temp>\.MD\scripts\gates\version-gate.ps1` (the resolver answers inside its own tree); the
   role `past-mistakes-library` is `PAST-MISTAKES-LIBRARY.md`; `session-start.py --print` emits the hook payload.
1. `gates\version-gate.ps1 -Action register` (with a `-PriorArt` note) - one identity: ledger key, repo folder, display name, the scanned version locations.
2. `version-gate.ps1 -Action bump -Kind patch` - the tool issues `1.0.0` for the example's first number and writes it into the repo; nothing was typed.
3. `release\changelog.ps1 -Action add` - the entry is written as the change happens (rule 61).
4. the package is laid out under `7. current test builds\Skyrim - Example Mod\Example Mod 1.0.0` with its README,
   LICENSE, NOTICE and CHANGELOG (`distro-names.ps1`'s `Resolve-PackageRoot` names the folder).
5. `gates\package-gate.ps1` evaluates every row of `gate-rules.json` against it - expected: `PASS  every rule clear`
   (the example is a Mod Organizer 2 plugin, so the rule that requires fault handling in every MO2 plugin applies
   to it and it carries the standard block).
6. `version-gate.ps1 -Action record -Status working` with evidence and the SHA-256 of the shipped file - a number is EARNED.
7. the repo is committed and tagged `v1.0.0` (rule 9), then `version-gate.ps1 -Action gate -Stage finalize` - it
   passes only because 6 and the tag happened.
8. a deliberate failure: a second package that ships a test script, a `.esl`, and an unparseable JSON, and lacks
   LICENSE and NOTICE; `package-gate.ps1` must REFUSE it (expected: it lists the hits, exit 1).
9. `bump -Kind patch` issues `1.0.1`, it is recorded `failed`, and `next` shows `1.0.1` again - a failed build never consumes a number.
10. `prune-test-builds.ps1` (dry run), `gate-ledger.ps1` records and scores a verdict, `rules-digest.py` regenerates
    the digest (70 rules), `logic-index.py --check` confirms the past-mistakes library's index is current and
    `gate-rules-index.py --check` the gate-rules index.
11. the render work pipeline, with no Blender and no game mesh (every mesh is made up by the test): `package-render.py`
    on the example package exits 0 (it ships no NIF); the self-tests of `package-render-gate.py`,
    `engraving-layout-gate.py`, `fomod-option-image-gate.py`, `surface-profile-gate.py`, `render\nif-readback.py` and
    `render\before-after-sheet.py`; the pattern library generates a small triquetra that `pattern-gate.py` passes and
    a seeded, too-coarse one that it refuses; `package_render_uv.py` passes an evenly mapped strip and fails the same
    strip with its UVs stretched; and Blender with PyNifly is found - or the step reports SKIP, which passes.

Every step prints `ok` or `FAIL` with the gate's own output, then a summary line: `PASS  (n checks)` or
`FAIL  (n of m)`. `example\expected-selftest-output.txt` is the output the kit's author got; compare yours to it.
The temp pipeline is deleted afterwards; the person's `<ROOT>` is untouched by the self-test.

If it fails, the failure is real: read the gate's message, fix the environment (usually Python missing from PATH or
an execution policy), rerun. Do not edit the self-test to make it pass.

## 7. The person's first mod - the loop the pipeline runs every day

With `<ROOT>` as the working folder and `$s = "<ROOT>\.MD\scripts"` (or ask by role:
`& (py -3 "<ROOT>\.MD\resolvers\resolve.py" find version-gate) -Action ...`):

```powershell
# once per mod: its source repo lives under "6. current wip mods\<RepoFolder>"
#   a new mod needs -PriorArt <file>: a note, written by the person or by you from a search they asked for, of what already
#   exists on Nexus and GitHub. The gate reads the note; the kit does no searching itself.
& "$s\gates\version-gate.ps1" -Action register -Mod MyMod -Repo MyMod -DisplayName "My Mod" -PriorArt "<that note>"

# every change
& "$s\gates\version-gate.ps1" -Action bump -Mod MyMod -Kind patch|minor|major   # issues the next number of that kind and writes every location (semantic versioning; -Kind is required)
& "$s\release\changelog.ps1"  -Action add -Mod MyMod -Version <the number bump printed> -Type Fixed -Entry "what changed"
#   build it; lay the package out where `resolve.py place test-build-package --var game=<Game> --var mod="My Mod"
#   --var version=<version>` says: "7. current test builds\<Game> - My Mod\My Mod <version>\"
& "$s\gates\package-gate.ps1" -Package "<that folder>"    # 0 hits or it does not ship
#   the person tests it; only THEN:
& "$s\gates\version-gate.ps1" -Action record -Mod MyMod -Version <version> -Status working -Evidence "what was observed, when" -Dll "<the built file>"
& "$s\release\pre-finalize-check.ps1" -ModName "My Mod"   # PASS/FAIL/WARN/SKIP per rule; a FAIL blocks
& "$s\release\finalize-mod.ps1" -Mod MyMod -DryRun         # then without -DryRun: gate, git tag, copy to
#   "10. finalized mods" + a verified zip, distro sync (version references, changelog, zip, banner pill), re-check,
#   prune old test builds - one command instead of the hand steps sync-nexus-distro.ps1 and the sweep used to need
& "$s\release\nexus-distro-sweep.ps1"                      # every distro folder holds exactly the newest zip
```

## 7b. Posting to Nexus Mods

The kit posts nothing. The person uploads through the page's own form, or through a tool they asked for in
`OPTIONAL-SCRIPTS.md`, and then the posting is recorded so the number is spent:

```powershell
& "$s\gates\version-gate.ps1" -Action posted -Mod MyMod -Version <version> -Channel nexus -File "<the zip>" -Evidence "<where it was posted>"
```

- The page text follows `templates\nexus-page-template.txt` and the `nexus-page` skill. That skill describes the original's
  browser-driven posting; here, a post is the person's to make unless they set up something else.
- A changelog entry on Nexus can be edited but not deleted or renamed; correct a wrong one in place.
- Keep a copy of any image before deleting or replacing it on a page: a deleted Nexus image cannot be put back.
- Every claim on a page must be true, and the page carries the site's AI tags if AI made the work.
- `scripts\ops\attention-ping.ps1` plays three notification sounds; the original's agent puts its question in chat first
  and then plays it, so the person can work on something else while it runs.

Numbers are semantic versions (rules part 03, rule 6): MAJOR.MINOR.PATCH, and `bump` will not run without `-Kind`.
`patch` is bug fixes only, `minor` is new functionality that stays backward compatible (resets the patch to 0), `major`
is a break (resets minor and patch). The agent decides the kind from what the release does for the people who use it,
never from how big the change felt. A posted number is spent; an open (unposted) number takes changes of its own or a
lower kind, and a higher-kind change withdraws it and re-issues from the last posted number (posted 1.2.4, open 1.2.5,
`bump -Kind minor` gives 1.3.0). There is no roll-over: 1.0.9 plus a patch is 1.0.10.

A failed or scratch build is recorded `-Status failed` or `scratch` and its number is REUSED by the next bump. That
is the rule the whole tool exists for: a version is earned by working, and a changelog has no gaps full of experiments.

## 7c. Skills - the procedures, loaded when the work starts (Claude Code)

The rules say WHAT must be true; `skills\` says HOW a kind of work is done, as Claude Code skills. Each `SKILL.md`
is a route: which rule part to read, which scripts to run in which order, which past-mistakes library topics to grep. It
copies no rule text (a rule lives in exactly one place), so a skill stays right when a rule is amended - as long as
the script names and arguments it lists still exist. The ten: `mod-release`, `nexus-page`, `in-game-test` (its `references\TESTING-PROTOCOL.md` is the test-run
protocol of rule 20),
`amf-menu-port` (its `references\SMF-CONVERSION-PLAYBOOK.md` is the settings-port playbook), `modding-tools` (with `skills\modding-tools\scripts\esm_lookup.py`, a FormID-by-EditorID reader - a
FormID is looked up, never recalled), `troubleshooting` (falsification and adversarial mode, rules 56, 57 and 49 - the procedures are its
`references\FALSIFICATION-MODE.md` and `references\ADVERSARIAL-MODE.md`), `session-records`,
`named-commands`, `skill-scout`, `weapon-engraving` (how carved decoration is laid out on a model part; its steps call the
pattern library, `scripts\art\patternlib`, and the engraving gates of section 7e).

Install them where every session finds them, with the source kept in the pipeline:

```powershell
foreach ($d in Get-ChildItem "<ROOT>\.MD\skills" -Directory) {
    cmd /c mklink /J "$env:USERPROFILE\.claude\skills\$($d.Name)" $d.FullName
}
```

A directory junction needs no admin rights; edit the skill under `<ROOT>\.MD\skills` and every session sees the
change. Many lines name the original's mods, MO2 instances and test tools - adapt those to the person's setup, the
same way section 9 says for the rules. Validate a skill after editing it: its header must be valid YAML (a colon
inside the `description` breaks it).

**Check:** a new Claude Code session lists the ten skills among its available skills.

## 7d. Finding what deserves a skill - `skill-scout.py`

```powershell
python -I "<ROOT>\.MD\scripts\skill-scout.py"          # report to <ROOT>\.MD\logs\skill-scout.md
python -I "<ROOT>\.MD\scripts\skill-scout.py" --todo   # also add NEW candidates to the to-do list
```

It reads the Claude Code transcripts (`~\.claude\projects\*\*.jsonl`) and flags what is repeated across three or
more sessions with no skill naming it: script chains, scripts run by hand, docs re-read, and the person's own
"from now on" / "every time you" instructions. It never writes a skill: each candidate is made a skill (or a line in
an existing one), a gate row if it is one checkable fact, a rule if it is an instruction - or put in
`scripts\skill-scout-ignore.txt` with the reason, and it is never flagged again. The original runs it daily as a
scheduled task and as a section of its optimisation sweep. The `skill-scout` skill is its manual.



## 7e. The render work pipeline - see what ships before it is posted (model mods)

For a mod that ships meshes (`.nif`). The order:

1. **Build** the meshes and textures (the person's own build scripts).
2. **Read the NIFs back**, no Blender: `scripts\render\nif-readback.py <package or folder> --tex-prefix textures\<mod>`
   (role `nif-readback`) fails on a block reference outside the file, a skinned shape without the skinned shader flag
   (it draws nothing), a texture path that resolves to no file, lost UVs or broken tangent frames, a hard edge
   smoothed over, light through the mesh and faces wound the wrong way. `niflib.py` (our own NIF reader) and
   `winding.py` (the face-direction check) sit beside it; `plugins\Inspect-NifShapes.py` lists a mesh's shapes and
   `plugins\Repath-NifTextures.py` rewrites its texture paths without breaking the block sizes.
3. **UV and engraving gates.** In the package gate, on every package (their `gate-rules.json` rows ship):
   `gates\nif-uv-overlap-gate.py` (two different pieces painted into the same atlas texels; texconv decodes the maps
   to judge whether it shows), `gates\esp-obnd-gate.py` (an item record with all-zero object bounds),
   `gates\fomod-option-image-gate.py` (an installer option that installs a model carries a picture of it) and
   `gates\engraving-layout-gate.py` (the engraving layout rule of the `weapon-engraving` skill). At design time:
   `scripts\art\patternlib` (role `patternlib-cli`: an engraving pattern from a JSON spec, validated - exit 2 when a
   validator refuses), `gates\pattern-gate.py` (re-validates a saved pattern) and `gates\surface-profile-gate.py`
   (a carved face whose shading wanders).
4. **Re-render the finalized package before posting:** `release\package-render.py --mod <key> --version X.Y.Z`
   (role `package-render`; `finalize-mod.ps1` runs it as its last station) renders every unique shipped NIF in
   Blender with the textures the package ships (`package_render_blender.py`), measures UV stretch on the shipped
   mesh (`package_render_uv.py`, numpy only), runs the design gates and writes sheets and `package-render.json` (the
   hash of every NIF and DDS) into the distro folder's `assets\package-renders\<version>\`. A package with no NIF
   passes at once. `gates\package-render-gate.py` refuses posting a model mod whose render is missing, failed, or
   made from other files than the package holds now; `package-render.py accept --reason "<the person's words>"`
   records a reviewed ruling on a flagged result.
5. **A before/after sheet for review:** `render\before-after-sheet.py render --before <nif> --before-tex <folder>
   --after <nif> --after-tex <folder>` renders both sides with one camera and light (`render\render_lib.py`:
   game-like TruePBR or classic shading) and lays them side by side; `sheet --row "label|before.png|after.png"`
   lays out pictures that already exist (a third picture per row for original / marks / result).
   `art\make-feature-banners.py` makes the page's feature banners from screenshots, each with its highlight box.

Without Blender the render steps say so: `before-after-sheet.py render` prints SKIP (exit 3) and `package-render.py`
exits 2 with "Blender not found". Nothing in the kit installs Blender, PyNifly or texconv.

**Check:** step 11 of the self-test passes.

## 8. When something goes wrong - the loop that makes the pipeline improve

1. Fix it.
2. Write the past-mistakes library entry (`PAST-MISTAKES-LIBRARY.md`): the symptom as the heading, what was believed,
   what was true, how it was caught. Run `python .MD\scripts\logic-index.py` to refresh its index block (the script
   asks the resolver for role `past-mistakes-library`). If the fix added a new MECHANISM to the pipeline, give it an
   entry in `LOGIC-LIBRARY.md` (the catalogue of logics) the same day too.
3. **The same day, if the mistake can be expressed as a check, add a rule row to `scripts\gate-rules.json`.** A row:

```json
{ "id": "no-test-scripts-in-packages", "kind": "forbid-path-regex",
  "pattern": "(?i)(^|[\\\\/])scripts[\\\\/][^\\\\/]*test[^\\\\/]*\\.(pex|psc)$",
  "exemptMods": [], "added": "2026-09-21",
  "why": "a test script shipped in a release zip; a test script never ships to players" }
```

   The kinds the runner understands are listed at the top of `scripts\gates\package-gate.ps1` (path and extension
   forbids, required file contents, previous-release file classes, archive-equals-folder, page-text rules, plugin
   header and record checks, JSON parses, repo-source require/forbid regexes, and more). If none fits, add a kind
   to the runner - it is small on purpose. A `package-script-passes` row names a helper script relative to
   `.MD\scripts` (`gates\xinput-import-gate.py`). Then `python .MD\scripts\gate-rules-index.py --build` refreshes
   `scripts\gate-rules-INDEX.md`.
4. Run `scripts\gate-sweep.ps1` over every package to see what the new rule catches that already shipped.
5. If the failure was a *known solution applied late*, it also earns a line in `PREFLIGHT.md` (hard cap: one screen;
   retire the line whose trigger fired least recently).

## 8b. The archive sweep - work left behind in old sessions

Sessions end, get archived, and take unwritten work with them. The sweep finds it:

1. `python -I "<ROOT>\.MD\scripts\ops\session-digest.py" --exclude <the current session's id>` writes one short digest
   per transcript into `<ROOT>\.MD\logs\session-digests\`: everything the person typed (typed turns and messages sent
   mid-turn; tool output and other sessions' text skipped) and the session's reports that name open work. Anything
   shaped like a key, token or authorization code is redacted as it writes - people paste credentials into chats,
   and a copy of a transcript copies them too. The digests quote the person verbatim: never commit or share them.
2. Batch the digests (~170 KB each, newest first) and give each batch to ONE checking agent, following
   `docs\ARCHIVE-SWEEP-INSTRUCTIONS.md`: each item becomes RESOLVED (with evidence), RECORDED (where), LOST (open and
   written nowhere), RULE-NOT-SAVED (a standing instruction in no rule or memory) or UNCLEAR, against the CURRENT
   files. The agents write only their report.
3. You spot-check the LOST items, then move them into the to-do list (quoting the person), save the instructions as
   rules or memories, commit work found uncommitted, and move finished to-do entries to Resolved.

The original's first sweep read 32 sessions (3.3 GB of transcripts, 1.3 MB of digests) and recovered 40 lost items,
including three weeks of uncommitted source and a licence label that contradicted a relicense.

## 10. What the kit deliberately leaves out

- Secrets. There is no key file and nothing reads a key.
- Every tool that reaches the internet (`OPTIONAL-SCRIPTS.md`).
- Direct evidence from other people's work: code, disassembly, byte signatures, offsets, record IDs, asset paths, quoted licence
  and wiki text. The original's console-command reference, which was compiled from public wikis, and its record of framework
  licence terms are gone too: go to the source for those.
- A rule, skill or library entry may name a tool that is not here: `health-gate`, `usage-pacing`, `combined-run`, `package-mod`,
  the DevBench, TestBench and gamelink test tools, a watcher, a bot, and others. If `resolve.py find <role>` does not know it,
  it is the original's. Do not report it as missing or try to run it. Tell the person what the rule wants done and do that by
  hand, or offer to write a local version, only where it touches no network.
- Gate rows whose helper script is not shipped were removed. The ones naming the original's page links were removed too.
- The owner's data: their ledgers, progress log, mod repos, test instances, memories. The ledgers ship EMPTY.
- The owner's roles: the rosters for their MO2 instances (`games.json`) and their one-off modlist scripts
  (`njordlinger.json`), every role naming a program at a fixed path on their machine, and every role whose file the
  kit does not ship. `resolvers\render-preamble.py` and `render-hooks.py` (they generate the original's sub-agent
  environment line and settings.json guard hooks from those roles) and the resolver's test fixtures stay out too.
- The owner's Mod Organizer 2 plugins (MO2 Keyword Tagger, MO2 Custom Filters, the Modlist Manager) - they are
  published on Nexus Mods under the author ApocryphaRealm and are not part of this kit.
- The in-game testing tools (the frame recorder, the live game link, the player bot) - machine-specific and out of
  scope for a first version; the rules that mention them (part 05, `PREFLIGHT.md`) are left intact as the standard
  they set.
- A C++ toolchain. Part 02 says how the original discovers one; installing it is the person's step.
- From the original's render work: its weapon sets' design workspace (the build, paint and measure scripts under
  `4. plans`), the mods' own build scripts and item tables, the mesh assemblers built on the game's own meshes, a
  shader block derived from another author's tool, and the Sketchfab tools (they reach the internet). What was
  generic was promoted into `scripts\render` first. Blender, PyNifly and texconv are the person's to install.
